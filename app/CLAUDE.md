# CLAUDE.md

## 项目概述

CLAUDE 是一个基于本地知识树和 网页版 AI 对话的对话系统。它通过将知识树中的节点作为对话的上下文，使用 AI 来生成回答，从而实现更结构化和有组织的对话体验。

---

### 你这个产品的本质

```
传统 AI 对话：
  用户 ←→ AI（一条直线，越聊越混乱）

你要做的：
       知识树（本地 Markdown 文件）
           │
      ┌────┼────┐
      │    │    │
     节点  节点  节点    ← 每个节点可以独立发起干净的对话
      │    │    │
    ┌─┴─┐  │  ┌─┴─┐
    │   │  │  │   │
   节点 节点 │ 节点 节点
            │
          ┌─┴─┐
          │   │
         节点 节点

AI 是"工具"，知识树才是"主体"。
```

### Markdown 节点文件格式设计

每个节点是一个 `.md` 文件，**Obsidian 完全兼容**，同时包含你的应用需要的结构化数据：

```markdown
---
id: "a1b2c3d4"
parent: "f5e6d7c8"
children: ["x9y8z7w6", "m3n4o5p6"]
created: "2025-07-12T10:30:00"
updated: "2025-07-12T14:20:00"
status: "understood"        # exploring | understood | needs-review
tags: ["quantum-computing", "qubit"]
summary: "量子比特与经典比特的核心区别在于叠加态和纠缠"
---

# 量子比特与经典比特的区别

## 🔍 问题
量子比特和经典比特有什么区别？

## 🤖 AI 回答

量子比特（qubit）与经典比特的根本区别在于：

1. **叠加态**：量子比特可以同时处于 0 和 1 的状态...
2. **纠缠**：两个量子比特可以产生纠缠关联...
3. **测量坍缩**：测量时叠加态会坍缩为确定值...

## 📝 我的笔记

> 这里是自己整理的内容，AI 原始回答可以在理解后精简

关键理解：
- 经典比特 = 开关（0 或 1）
- 量子比特 = 旋转的硬币（既是正面也是反面，直到你去看它）

## 🔗 相关节点
- [[叠加态详解]]
- [[量子纠缠入门]]
```

**设计要点：**

- `frontmatter` 中的 `parent` 和 `children` 是你应用读写树结构的依据
- `summary` 字段是上下文管理器用来构建干净 Prompt 的关键
- `status` 用于标记学习进度
- 正文部分分为"问题 / AI 回答 / 我的笔记"三段，用户可以在"我的笔记"部分自由编辑
- Obsidian 中用 `[[链接]]` 可以直接跳转，完全兼容

### 上下文管理策略（核心难点）

这是你这个产品最关键的能力，也是区别于普通 AI 对话的地方：

```
场景：你想在"量子纠缠"节点重新发起对话

步骤 1：提取父节点链
  根节点"量子计算入门" 
    → 子节点"量子比特基础"
      → 子节点"量子纠缠"（当前位置）

步骤 2：构建上下文
  不是把所有历史对话丢给 AI，而是提取摘要：

  ┌────────────────────────────────────────┐
  │ 知识背景摘要：                            │
  │                                        │
  │ · 话题根：量子计算入门                      │
  │   摘要：了解了量子计算的基本概念和应用前景     │
  │                                        │
  │ · 上一步：量子比特基础                      │
  │   摘要：理解了量子比特的叠加态特性，           │
  │        以及与经典比特的本质区别              │
  │                                        │
  │ · 当前探索方向：量子纠缠                    │
  │                                        │
  │ 请基于以上背景回答以下问题...               │
  └────────────────────────────────────────┘

步骤 3：通过 Playwright 发送干净的新对话
  - 不是续接旧对话（避免上下文污染）
  - 而是全新的对话，但携带精炼的背景信息
```

**实现逻辑（伪代码）：**

```python
def build_context(current_node_id):
    chain = []
    node = get_node(current_node_id)
    
    # 向上遍历到根节点
    while node.parent:
        chain.prepend({
            "title": node.title,
            "summary": node.summary   # frontmatter 中的摘要
        })
        node = get_node(node.parent)
    
    # 构建 prompt
    prompt = "知识背景摘要：\n"
    for i, item in enumerate(chain):
        indent = "  " * i
        prompt += f"{indent}· {item['title']}：{item['summary']}\n"
    
    prompt += f"\n当前问题：{current_node.question}\n"
    prompt += "请基于以上背景，给出清晰、有针对性的回答。"
    
    return prompt
```

### 知识树操作设计

你需要的三种核心操作：

**裁剪（Cut）**

```
操作前：                    操作后：
    A                         A
    ├── B                     ├── B
    │   ├── D                 │   └── D
    │   └── E  ← 裁剪掉       └── C
    └── C

实现：
  1. 前端选中节点 E，点击"裁剪"
  2. 后端：从 B 的 frontmatter children 中移除 E
  3. 后端：删除 E.md 文件（或移动到回收站目录）
  4. 如果 E 有子节点，提示用户选择：一起删除 / 提升为 B 的子节点
```

**拼接（Splice/Merge）**

```
操作前：                    操作后：
  A       X                 A
  ├── B   ├── Y             ├── B
  └── C   └── Z             │   └── X
                            │       ├── Y
                            │       └── Z
                            └── C

实现：
  1. 前端拖动节点 X 到节点 B 下
  2. 后端：修改 X 的 parent 为 B
  3. 后端：将 X 加入 B 的 children 列表
  4. 后端：从 X 原父节点的 children 中移除 X
```

**移动（Move）**

```
实现：
  1. 前端拖动节点到新父节点上
  2. 后端更新双方的 parent/children 字段
  3. .md 文件本身不需要移动位置（文件夹层级由应用逻辑维护，
     或者你可以选择物理目录也对应树结构）
```

## deepseek网页自动化模块概述

基于 Playwright 的 DeepSeek 网页版 CLI 客户端。自动化操作 DeepSeek 聊天页面，支持文本问答、模型切换、图片上传（文件/剪贴板），可模块导入也可命令行直接使用。

- 入口文件：`dsweb.py`
- 依赖：`playwright`（必需）、`Pillow`（可选，`--image` 功能需要）
- Python ≥ 3.10

## to_obsidian_canvas — DS JSON → Obsidian Canvas 转换器

位于项目根目录 `to_obsidian_canvas/`，独立模块，不依赖后端服务。

### 功能

将 DeepSeek 前端导出的对话 JSON 转换为：
1. **一问一答 `.md` 笔记** — 每个 user+assistant 配对 = 一个 Obsidian 兼容的 Markdown 节点
2. **一个 `.canvas` 文件** — file 节点 + edge 还原对话树，可在 Obsidian 中可视化编辑

### 数据流

```
DS 导出 JSON (tempdata/*.json)
  │  parent 引用 → 配对 → 树结构推断
  ▼
converter.py
  │
  ├── .md 文件（每轮对话一个）
  │   ├── frontmatter: tags, user_msg_id, assistant_msg_id,
  │   │                 user_parent, assistant_parent, original_question
  │   ├── ## ❓ 用户问题
  │   ├── ## 🤖 AI 回答
  │   └── ## 💭 思考过程（> [!info]- callout，默认折叠）
  │
  └── .canvas 文件
      ├── "type": "file" 节点 → 指向对应 .md
      └── edge → 还原对话分支树
```

### 核心逻辑

| 步骤 | 说明 |
|------|------|
| 配对 | user 消息 + assistant.parent==user_idx 的 assistant → 一问一答节点 |
| 树结构 | user.parent → 数组索引 → 找到所在配对 → 该配对为 canvas 父节点 |
| 标签 | root（无父）/ branch（有父有子）/ leaf（有父无子）|
| 布局 | 自底向上递归树布局（TB 方向），叶子从左到右排，内部节点居中 |

### 输出结构

```
output/{对话标题}/           # 标题从 JSON 文件名提取（去日期）
  ├── {用户问题}.md
  ├── ...
  └── {对话标题}.canvas
```

### 使用

```bash
python to_obsidian_canvas/converter.py <json文件> [-o <输出目录>] [--vault-base <前缀>]
```

`--vault-base` 指定 Canvas `file` 字段的 vault 相对路径前缀，默认 `"{对话标题}/"`。

### 关键设计决策

- **不修改原始 message_id / parent 值** — 原样保留在 frontmatter 中
- **文件名 = 用户问题 sanitize** — 可修改，original_question 字段用于覆盖识别
- **reasoning_content 默认折叠** — Obsidian `[!info]-` callout
- **独立模块** — 不依赖 app/ 后端，纯本地文件操作
